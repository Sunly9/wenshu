# 项目方案：DocMind · 文档知识库问答引擎

> 本方案取代 `docs/项目方案-RepoChat.md`（代码仓库问答方向已归档，可作为后续"多数据源"扩展）。

---

## 一、项目定位

**不是"上传 PDF 然后问答"，而是一个把分片与检索策略做到可对比、可验证的知识库引擎。**

核心主张（也是简历上的开场白）：

> 知识库答不准，绝大多数时候不是模型不行，而是分片和检索没做好。

### 功能清单

| 模块 | 功能 |
|---|---|
| 文档接入 | 上传 PDF / Word / Markdown / TXT，或粘贴网页链接 |
| 解析 | 版面还原、标题层级抽取、**表格整块保留**、页眉页脚剔除 |
| 分片 | 4 种策略可切换，支持在前端实时预览切分结果 |
| 索引 | 向量 + 全文双索引，写入元数据（文件 / 章节路径 / 页码 / 块序号） |
| 检索 | 双路召回 → RRF 融合 → Rerank 重排 → 上下文组装 |
| 问答 | SSE 流式输出，**每句话带引用，可点开对应原文片段** |
| 检索调试台 | 可视化每次检索的完整过程与各项得分（差异化核心） |
| 评测面板 | 上传评测集，一键跑分，输出消融实验对比表（差异化核心） |

### 差异化三件套（缺一不可）

1. **检索调试台**：把 RAG 的黑盒打开。输入问题后，能看到召回的每个 chunk、它的向量分 / 关键词分 / 融合分 / 重排分，以及最终选中了哪几条。99% 的同类项目没有这一页。
2. **评测面板 + 消融实验表**：能拿出"naive 分块 62% → 结构感知 79% → +混合检索 86% → +Rerank 91%"这样一张表。**这张表就是简历的核心资产。**
3. **引用可溯源**：回答里每句话都能追溯到原文的文件、章节、页码。

## 二、分片策略（项目技术核心之一）

| 策略 | 原理 | 优点 | 缺点 | 定位 |
|---|---|---|---|---|
| 固定长度 | 按 N 个字符硬切 | 快、实现简单 | 切断句子与表格 | **仅作基线对照组** |
| 递归分隔符 | 按 `\n\n` → `\n` → `。` 层级递归找断点 | 落在自然边界 | 不感知文档结构 | 工程默认值 |
| 结构感知 | 按 Markdown 标题 / PDF 版面 / 表格 / 列表切 | 语义单元完整 | 需实现解析器 | **本项目主策略** |
| 语义分块 | 句子向量化，相似度骤降处断点 | 边界贴合语义 | 索引期成本高 | 对比实验项 |

### 两个拉开差距的进阶做法

**父子分块（Small-to-Big）**
- 用 256~384 token 的小块建索引（语义集中 → 命中准）
- 命中后返回其所属的 1024 token 父块给模型（上下文完整 → 答得全）
- 解决了"检索精度"与"上下文完整性"的矛盾，这是多数同类项目缺失的一层

**上下文增强分块（Contextual Retrieval）**
- 建索引时用 LLM 为每个块生成一句前缀："此段出自《XX》第三章，讲述……"
- 把前缀拼进块内容后再向量化
- 效果：彻底脱离上下文的孤立段落（如"如上所述，该值应设为 3"）也能被正确检索
- 该做法在中文技术社区讨论度低，面试时属于亮点

### 必带元数据

`document_id` / `file_name` / `section_path`（章节 breadcrumb）/ `page_no` / `chunk_index` / `parent_chunk_id` / `created_at`

用途：检索时可做元数据过滤，回答时可生成引用。

### 推荐组合（落地方案）

```
结构感知切分
  → 子块 256~384 token，15% overlap
  → 拼接章节路径前缀 + LLM 上下文前缀
  → 子块入向量索引与全文索引，父块入库
  → 双路召回各 50 条
  → RRF 融合约 30 条
  → Rerank 保留 8 条
  → 去重合并父块，取 4 条组装上下文
```

## 三、检索策略（项目技术核心之二）

| 手段 | 作用 | 预期收益 |
|---|---|---|
| 向量 + 关键词双路召回 | 语义匹配 + 精确术语匹配互补 | 基础项 |
| RRF 融合 | 无需调权即可合并两路排名 | 中等 |
| **Rerank 重排** | 交叉编码器精排，矫正向量召回偏差 | **单一手段中收益最大** |
| 查询改写 / 多查询 | 补全口语化提问，扩展同义表达 | 中等 |
| 元数据过滤 | 限定文件、时间、章节范围 | 场景相关 |
| 上下文压缩 | 剔除无关段落，降低噪声与 token 消耗 | 中等 |
| HyDE | 先生成假想答案再检索 | 可选实验项 |

## 四、评测体系（简历的杀手锏）

### 评测集

手工构造 50 条问题，每条包含：

| 字段 | 说明 |
|---|---|
| `question` | 用户提问（覆盖事实型 / 多跳 / 表格型 / 无答案型） |
| `gold_chunk_ids` | 标准答案所在的 chunk（人工标注） |
| `gold_answer` | 参考答案要点 |
| `type` | 题型分类，便于分维度分析 |

### 指标

- **Hit Rate@5**：标准 chunk 是否进入前 5，主指标
- **MRR**：标准 chunk 的平均倒数排名
- **引用准确率**：回答中引用是否真支撑该句结论
- **忠实度**：回答是否全部有原文依据（用 LLM 做裁判）

### 消融实验表（填完就是简历正文）

| 配置 | HitRate@5 | MRR | 引用准确率 |
|---|---|---|---|
| 固定 512 分块 + 纯向量召回 | 待测 | 待测 | 待测 |
| 递归分隔符 + 纯向量 | 待测 | 待测 | 待测 |
| 结构感知分块 + 纯向量 | 待测 | 待测 | 待测 |
| + 父子分块 | 待测 | 待测 | 待测 |
| + 双路召回 + RRF | 待测 | 待测 | 待测 |
| + Rerank | 待测 | 待测 | 待测 |
| + 上下文增强分块 | 待测 | 待测 | 待测 |

> 表中每一行只在上行基础上加一个变量，这是"消融实验"的标准做法，也是面试时最容易被追问的部分——提前想清楚每个变量的原理与代价。

## 五、技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Vue 3 + Vite + TypeScript + Element Plus | SSE 流式渲染、调试台可视化 |
| 后端 | Spring Boot 3.x，Java 21 LTS | 对外 REST + SSE |
| 文档解析 | Apache PDFBox（PDF）、flexmark（Markdown）、POI（Word）、jsoup（网页） | 表格需单独处理 |
| 向量库 | PostgreSQL 17 + pgvector | 向量与业务数据同库，减少运维 |
| 全文索引 | PostgreSQL tsvector（代码/英文）+ zhparser 或 jieba 分词（中文） | 中文全文检索的关键 |
| 缓存 / 队列 | Redis | 限流、异步索引任务、结果缓存 |
| Embedding | bge-small-zh-v1.5，ONNX 跑 CPU | 512 维，约 100MB，核显机器可跑 |
| Rerank | bge-reranker-base，ONNX 跑 CPU | 可降级为纯 RRF 融合 |
| 生成模型 | DeepSeek API | 成本极低 |
| 部署 | Docker Compose + GitHub Actions + GHCR | 详见 `docs/02-云服务器部署与CI-CD.md` |

## 六、数据模型（核心表）

```
knowledge_base (id, name, owner_id, created_at)

document (id, kb_id, file_name, file_type, size, page_count,
          status[PENDING/PARSING/INDEXING/READY/FAILED],
          chunk_strategy, created_at)

chunk (id, document_id, parent_id, content, token_count,
       section_path, page_no, chunk_index,
       embedding vector(512), content_tsv tsvector)

eval_question (id, kb_id, question, type, gold_chunk_ids, gold_answer)

query_log (id, kb_id, user_ip, question, retrieved_ids, rerank_scores,
           chosen_ids, answer, latency_ms, token_cost, created_at)
```

`query_log` 是检索调试台的数据来源，务必完整落库。

## 七、接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/kb` | 创建知识库 |
| POST | `/api/kb/{id}/documents` | 上传文档（异步解析） |
| GET | `/api/documents/{id}/status` | 轮询解析进度（或走 SSE） |
| POST | `/api/kb/{id}/chunks/preview` | **分片预览**：不入库，先看切分效果 |
| POST | `/api/chat` | 提问，SSE 流式返回 |
| GET | `/api/debug/{queryId}` | **检索调试**：返回完整召回与打分详情 |
| POST | `/api/eval/run` | 跑评测集，返回指标 |
| GET | `/api/eval/report/{runId}` | 获取消融实验报告 |

## 十、面试追问准备

| 追问 | 准备方向 |
|---|---|
| 为什么不用 LangChain / LlamaIndex？ | 能说清自己实现的每一步，比调框架更有说服力；框架的默认分片并不适合中文文档 |
| Rerank 为什么能提升？代价是什么？ | 交叉编码器逐对打分更准；代价是延迟增加，需限制候选集规模 |
| 中文全文检索怎么做的？ | 分词器选择、与向量的互补性（专有名词、编号类查询靠关键词） |
| 块大小怎么定的？ | 实验得出结论，而非拍脑袋；说明 token 数与召回精度、上下文完整性的权衡 |
| 怎么防止模型瞎编？ | 引用约束、无答案时明确拒答、忠实度评测 |
| 怎么知道效果变好了？ | **拿出消融实验表**，这是最有力的回答 |
